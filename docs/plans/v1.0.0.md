# Version 1.0.0 plan: command and orchestration

## Status

Approved product direction. Implementation begins only after the 0.5.0 stabilization gate passes and the installed cmux command-input surface has been documented with fixtures and failure semantics.

## Product promise

Version 1.0.0 makes cmux Agent Orchestrator useful as a daily command desk, not only an inventory or Kanban projection. A user can understand what an exact coding-agent session needs, send that session a follow-up instruction, and keep durable work aligned without surrendering control to hidden automation.

## Locked product decisions

- cmux remains the visible terminal and process owner.
- The plugin targets one canonical workspace, pane, surface, and provider conversation at a time.
- There is no broadcast action in 1.0.0.
- Terminal instructions always originate from an explicit user action.
- A delivery receipt proves only what the transport can verify; it never claims the agent understood, accepted, or completed an instruction.
- Deterministic evidence and policy own workflow automation. An LLM may propose actions but is not the source of truth.
- The optional AI coordinator is off by default.
- No runtime signal or AI judgment can move a task to Done.

## Workstream 1: exact-session instructions

### User experience

- Add `Send instruction...` to an exact Agent run and linked Work card.
- Open a native modal containing the conversation title, repository, current lifecycle state, and exact cmux target.
- Accept a multiline instruction without interpreting it as shell syntax.
- Offer `Send` and `Send & focus` actions.
- Make busy, waiting, unknown, missing, and replaced-target conditions explicit before delivery.
- Keep instruction history memory-only by default; never copy prompt text into Markdown or plugin data implicitly.

### Target and delivery contract

Immediately before delivery:

1. Refresh authoritative cmux topology.
2. Resolve the complete canonical workspace, pane, and surface tuple exactly once.
3. Revalidate the expected provider and provider conversation when one is known.
4. Reject a missing, ambiguous, changed, or reused target.
5. Invoke only the feature-detected cmux input primitive with an executable plus exact argument array and `shell: false`.
6. Separate text insertion from submission when the cmux contract permits it.
7. Bound execution time, output, retries, and postcondition checks.

The UI distinguishes `not sent`, `delivered to terminal`, `delivery unverified`, and `rejected`. It does not manufacture an agent acknowledgement.

### Failure behavior

- Never retry a potentially delivered instruction automatically.
- Never redirect an instruction to a repository-equivalent or title-equivalent surface.
- If delivery succeeds but focus or foreground activation fails, report the partial success without sending again.
- If identity changes between composition and submission, preserve the draft and require the user to select the new target explicitly.

## Workstream 2: deterministic workflow loop

The common workflow should not require an AI coordinator:

- Sending the first accepted instruction may propose or explicitly apply `Backlog -> Active`.
- Fresh structured Working evidence may move `Review -> Active` under the selected automation policy.
- Fresh structured turn-finished evidence may move `Active -> Review` under the selected automation policy.
- A finished turn creates a Needs-attention signal until it is acknowledged or superseded.
- Sending a follow-up from Review returns the task to Active as part of the explicit send action.
- Parked and Done remain manual.

Workflow state, runtime state, attention, transport delivery, and human acknowledgement remain separate fields. Viewing a cmux tab may clear an ephemeral read signal when cmux proves it, but it cannot alone mutate durable workflow.

## Workstream 3: optional AI coordinator

### Modes

- **Off**: default; starts no coordinator, performs no model work, and adds no cost.
- **On demand**: runs only after the user asks to analyze the board, a task, or selected sessions.
- **Automatic suggestions**: runs only for configured meaningful events, such as a fresh turn finish or blocked/needs-input signal.

### Operating boundary

- Let the user select an available provider rather than requiring one vendor.
- Keep the coordinator visible, identifiable, stoppable, and separate from the sessions it advises; do not hide an uncontrolled background agent.
- Supply bounded structured facts and user-approved context rather than unrestricted vault contents or complete transcripts.
- Request structured output containing the target task, proposed transition or follow-up instruction, rationale, confidence, and evidence references.
- Validate every returned task and session identity against current local authority.
- Present proposals for approval; the first 1.0.0 implementation does not grant the coordinator direct terminal-send or Done authority.

### Cost and loop controls

- Provide a global enable toggle and immediate stop control.
- Configure provider, trigger mode, cooldown, and maximum coordinator runs per day.
- Run no repeating model poll.
- Perform no silent retry after a model or transport failure.
- Allow at most one coordinator evaluation for one event generation.
- Detect and reject self-targeting, coordinator-to-coordinator, and repeated unchanged proposals.
- Show the last run time, trigger, outcome, and whether any proposal remains pending.

## Workstream 4: trust, onboarding, and compatibility

- Explain separately the permissions used for observation, foreground activation, terminal input, and optional AI coordination.
- Keep command authority disabled until the user completes a successful exact-target test.
- Provide privacy-safe diagnostics that omit prompts, terminal text, vault content, credentials, and provider transcripts.
- Preserve schema migration from every released 0.x version.
- Preserve task notes and run history when command or coordinator features are disabled.
- Support the documented legacy snapshot path for observation; gate unsupported command features visibly instead of degrading to unsafe alternatives.
- Document how to recover drafts and state after Obsidian, cmux, or a provider exits during an operation.

## Architecture boundaries

```text
cmux/provider evidence -> deterministic reducer -> workflow proposal policy
                                                     |
Obsidian user -> instruction composer -> target guard -> cmux input adapter
                         ^                           |
                         |                           v
                optional AI coordinator      exact provider surface
                    proposals only
```

- Observation adapters cannot write workflow or send input.
- The target guard cannot infer a replacement destination.
- The input adapter cannot read Markdown or choose instructions.
- The coordinator cannot bypass the target guard or workflow policy.
- The task repository remains the only durable workflow writer.

## Non-goals for 1.0.0

- Hosting an embedded PTY.
- Replacing cmux as process owner.
- Unattended multi-agent broadcast or swarm scheduling.
- A hosted account, telemetry backend, or remote transcript service.
- General shell execution from Markdown.
- Automatic task completion based on lifecycle output or LLM opinion.

## Implementation sequence

1. Document and fixture the supported cmux input capability and failure behavior.
2. Implement a transport-neutral instruction and delivery-result contract.
3. Add exact target revalidation and adversarial surface-reuse tests.
4. Add the instruction composer and single-target delivery UI.
5. Connect explicit sends to guarded deterministic workflow transitions.
6. Add onboarding, permissions, diagnostics, and recovery UX.
7. Implement the optional coordinator in Off and On-demand modes.
8. Add bounded Automatic-suggestions mode only after proposal deduplication and loop controls pass.
9. Run migration, compatibility, accessibility, privacy, failure-injection, and local end-to-end verification.

Each step lands independently with focused tests. Command transport and coordinator work must not be hidden inside UI-only commits.

## 1.0.0 release criteria

- An instruction can reach one intended supported session without shell interpolation or target ambiguity.
- No stale, reused, missing, or conflicting target receives input.
- Retrying the UI cannot duplicate a possibly delivered instruction.
- Focus and foreground activation failures cannot cause a second delivery.
- Disabled coordinator mode starts no model process and performs no coordinator work.
- On-demand and automatic suggestions obey the configured run limit, cooldown, and generation deduplication.
- Coordinator output cannot write workflow or send terminal input without the same guarded user-facing path.
- Existing 0.x tasks, bindings, settings, and run history migrate without duplication or loss.
- All actions remain understandable with long titles, narrow panes, keyboard-only navigation, and supported Obsidian themes.
- Security documentation, screenshots, release assets, provenance attestations, and Community Directory metadata match the shipped behavior.
